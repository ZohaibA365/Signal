The outreach agent

What it does

For each posting scored above a threshold: look up whether it has been approached, draft three messages if not, record the outcome. Three tool calls, decided by the model, permitted or refused by code. The one status it can write is email_drafted.

check_application_status(job_id) → status, company, fit_score, eligible_to_draft, reason draft_outreach_email(job_id, company) → three variants, and the verification verdict on each update_tracker_status(job_id, new_status, notes) → the transition, if the agent is allowed to make it send_email deliberately absent

company is an argument the model must supply and the code then checks against the database. It exists to be checked. A model that produces a company from anywhere other than the previous tool result is caught by exactly that mismatch.

The rails

Each is enforced in code. None depends on the model following instructions, because the working assumption is that it might not.

RailWhat it stops
Checked twice Whether a posting may be drafted for is computed in the status tool and checked again, independently, inside the draft tool. Enforcing it in one place would make it advice: the model could skip the check to get past it.
Never trust a model value Anything that should have come from the database is compared against it. A company the model invented is rejected, not quietly corrected. A posting id that exists nowhere gets no record created for it.
One legal transition Only not_contacted → email_drafted. "Sent" and "responded" describe things a person did in the world; an agent able to write them could report an email it never sent, and the tracker would become a record of fiction.
A status must be earned Recording a posting as drafted is refused unless a draft exists. This rail was written because the first run marked one as drafted after its draft call had been rejected.
Eight calls per posting Per posting, not per run — the expected path is three, so a cap across a batch would stop it two postings in. Hitting the cap is recorded as an outcome, not an error: it is information about the model.
No fatal failures A tool never raises into the loop. Bad arguments, a missing posting, a database error and a model failure all become a recorded result and the run continues. One bad posting must not take a batch with it.

Letting a model write, without letting it invent

Every message used to be assembled deterministically from records that came out of SQL, so by construction it could not contain a figure the warehouse cannot reproduce. That reads a little mechanically. A model writes better sentences — and would throw that guarantee away, unless something checks.

So the model drafts from the records, and then the draft is proved against them. Every number must trace to an observation, the link must be exact, the company must be named, the channel budgets must hold, and the playbook's prohibitions are enforced. A draft that fails is discarded, the deterministic version is used instead, and the rejected text is kept — because "the model fabricated something" is not actionable, and the sentence it fabricated is.

Accepted

Every figure appears in an observation. A correct rounding counts: an observation reading 12.1x permits 12x, because the reader is not misled.

Rejected

A figure that appears nowhere. 13x against the same observation is an invention, not a rounding, and the draft is thrown away.

observation: they mention Tableau in 24% of their postings, about 12.1x the rate across the companies I track model wrote: "...emphasizes Tableau 12x more than peers" → accepted model wrote: "...grew headcount 47% this year" → rejected model wrote: "see https://tdbank.com/careers" → rejected model wrote: "I interned at TD Bank last summer" → rejected

What this does not prove. It proves every number in the text appears in the source records. It cannot prove the sentence around the number is a fair reading of it — "hiring has collapsed to 12 roles" and "hiring is up to 12 roles" both pass. Numeric grounding is necessary, not sufficient.

What a run leaves behind

Every tool call is recorded with its arguments, result, duration and outcome, including the rejected ones, which are the interesting ones. A run can be reconstructed exactly: what was attempted, what was refused, and which drafts came from the model rather than the template.

check_application_status ok not_contacted; drafting allowed draft_outreach_email ok 6 insight(s), drafted by the model update_tracker_status ok not_contacted → email_drafted and on a second pass over the same posting: check_application_status ok email_drafted; drafting blocked

Where the model is not used

Choosing among three tools and passing an identifier through is the cheapest thing a model can be asked to do, so the orchestration runs on the small one. The judgement that actually needs a capable model is elsewhere on this site: reading a posting to decide whether a candidate could legally hold the role.

And the honest note, since it is the first thing worth asking: the orchestration does not need a model at all. Check, draft, record is a loop. What the model earns its place for is the prose — which is also the only part that had to be proved before it could be trusted.
